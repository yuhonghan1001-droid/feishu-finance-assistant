## 2. 项目过程中出现的主要问题

### 2.1 最初只有网页原型，无法在飞书交流

项目最初具备网页展示和本地问答界面，但没有飞书事件接收、身份校验、消息解析和机器人回复能力，同事无法在飞书中直接咨询。

### 2.2 Webhook 部署条件不稳定

飞书 Webhook 需要可由飞书服务器访问的公网 HTTPS 地址，并需要处理验证令牌、事件签名和加密消息。当前运行环境不适合长期暴露稳定公网回调地址，因此仅有 Webhook 代码还不能保证机器人持续在线。

### 2.3 机器人出现“不回复”

排查中遇到过以下情况：

- 飞书长连接进程没有启动或已经退出。
- macOS 登录常驻服务没有成功加载。
- Codex 受限运行环境无法解析或访问 `open.feishu.cn`。
- 同一项目曾存在旧进程、测试进程和新进程并存，需要区分实时日志与历史日志。

最终通过检查进程文件句柄、网络套接字和飞书回复日志，确认有效机器人进程已经建立到飞书的 TCP 连接并能够回复消息。

### 2.4 公司制度类问题被统一拒答

早期知识库只覆盖少量发票和个税问题。员工询问差旅报销、员工代垫、预算申请、采购付款或业务招待审批时，机器人容易统一返回“需要内部制度、无法给出结论”，实际帮助有限。

### 2.5 随便提问时经常得到同一套兜底话术

`findAnswer` 的关键词覆盖不足，合同税务、预算、代垫、福利费、招待费等问法无法正确路由。没有命中知识库时，机器人会反复输出相同的不确定性模板，形成“问什么都回复同一段”的体验。

### 2.6 外部大模型 API 没有真正可用

项目曾接入 OpenAI Responses API，但实际提供的密钥属于其他平台，调用官方 OpenAI 接口返回鉴权失败。结果是每条消息先等待外部接口失败，再回退到知识库，不仅没有增加回答能力，还影响响应速度和稳定性。

### 2.7 税务知识不够完整，而且存在年度口径变化

原知识库重点集中在发票、个税汇算和专项附加扣除，缺少企业日常高频税务问题。2026 年增值税法施行后，小规模纳税人起征点、进项抵扣等口径也发生变化，继续使用旧模板存在答错风险。

### 2.8 当前机器的长期运行仍有环境约束

长连接机器人依赖承载电脑保持开机和联网。当前 `launchctl` 登录常驻注册在受限会话中会返回 I/O error；虽然现有进程已经连接飞书并能回复，但日志中仍出现过间歇性 DNS 解析错误，后续需要持续监控或迁移到稳定服务器。

## 4. 当前系统结构

```text
员工在飞书提问
    ↓
飞书长连接接收消息
    ↓
提取文本、去除 @机器人、消息去重
    ↓
FINANCE_ASSISTANT_MODE
    ├─ knowledge → 本地审核知识库 → 生成带政策依据的答案
    └─ ai        → 本地知识库作为参考 → 外部模型组织答案
                         ↓ 失败
                    本地知识库降级
    ↓
飞书机器人回复
```

当前生产运行使用 `knowledge` 路径。

## 5. 采用的改进方法

### 5.1 公开规则优先采用官方依据

税率、扣除比例、申报期限和有效期等易变化内容优先采用全国人大、中国政府网、财政部和国家税务总局来源。正文独立回答问题；用户询问依据、法规或原文时再展示链接。

### 5.2 把公开规则、通用做法和公司制度分开

- 公开规则：可以根据有效法律政策明确回答。
- 通用企业做法：可以给出多数企业适用的流程，但不能声称是本公司正式制度。
- 公司制度：额度、审批人、材料和时限需要接入真实内部文件后才能确定。

### 5.3 外部能力失败时保持核心功能

外部 API 不可用时不让机器人整体失效，而是切换到经过审核的本地知识库，避免每次消息都等待鉴权失败。

### 5.4 每次功能变更配套测试

测试覆盖网页渲染、飞书验证、加密事件、消息回复、知识路由、通用内部流程、模型请求、对话历史、网页引用和失败降级。

### 5.5 配置与密钥不写入源码

飞书密钥和模型密钥保存在 Git 忽略的本地环境文件中；脚本修改配置时不打印完整密钥，并维持严格文件权限。
